一、工作原则

1. 默认只读审查，不修改业务代码、配置、数据库、依赖、Git 状态或用户数据。
2. 可以执行安全、非破坏性的检查，例如：读取文件、搜索代码、查看 Git 状态、运行已有的 lint、类型检查和测试。
3. 不要为了让测试通过而偷偷修改代码，不要删除或覆盖现有文件。
4. 如果测试需要联网、真实 API Key、付费服务、生产数据、启动外部服务或可能产生副作用，请不要擅自执行；在报告中说明限制和建议的验证方式。
5. 不要仅依据 README、注释或接口名称判断功能已实现，必须核对实际代码、调用链、数据库结构、前端入口和测试。
6. 所有重要结论必须给出证据：文件路径、类名、函数名、接口、组件名，必要时标出行号。
7. 区分“已确认问题”“高概率问题”“设计风险”“优化建议”，不要把猜测写成事实。
8. 不要只列问题；每个问题都应说明影响、触发条件、根因、修复建议和验证方式。
9. 遇到大型项目时先建立项目地图，再按模块审查，不要只检查少量显眼文件。
10. 开始审查前先读取仓库中的 AGENTS.md、README、开发文档、任务记录和项目约定；若规则冲突，以更高优先级指令为准。

四、审查范围

A. 项目结构与架构

- 目录划分是否清晰，模块边界是否合理；
- 表现层、业务层、数据访问层和基础设施层是否过度耦合；
- 是否存在循环依赖、跨层调用、重复模块、巨型文件或职责混乱；
- 配置、常量、异常、日志、Schema、模型和服务是否组织合理；
- 同步与异步代码是否正确组合；
- Session、事务、请求作用域和后台/流式任务的生命周期是否安全；
- 前端状态管理、请求层、页面、组件和领域类型是否边界清晰；
- 当前架构能否支持新增 Provider、模型类型、检索策略、向量数据库和部署方式。

B. 功能完整性

逐项追踪用户可见功能，至少检查：

- 注册、登录、刷新令牌、退出、权限校验和登录态恢复；
- AI 服务连接的新增、编辑、删除、测试、凭据加密与地区配置；
- Provider 模型目录的自动获取、刷新、缓存、筛选、手动模型回退和错误提示；
- 模型类型识别：聊天/文本生成、多模态、图片生成、语音识别、语音合成、向量嵌入、重排序等；
- 普通聊天、流式响应、会话创建、重命名、切换、删除和消息持久化；
- 知识库创建、文件上传、解析、切分、嵌入、索引、检索、引用和删除；
- grounded_chat 等工作流所需参数、前端入口和服务端校验是否一致；
- 设置、错误页、空状态、加载状态、重试机制和操作反馈；
- 文档、README、界面或注释中提到的所有能力是否真的可达、可用且完成闭环。

为核心功能建立“功能—前端入口—API—服务—数据层—测试”追踪表，标记：已实现、部分实现、不可达、占位实现、未实现、无法验证。

C. Bug 与正确性

重点查找：

- 可稳定复现的运行时异常、500、401、403、404、409、422；
- 前后端字段名、类型、枚举、必填项和默认值不一致；
- SQLAlchemy DetachedInstanceError、Session 提前关闭、延迟加载和事务边界问题；
- StreamingResponse/SSE 中闭包捕获已脱离 Session 对象的问题；
- 第一次失败、第二次成功的竞态、初始化时序或缓存问题；
- 删除当前聊天后仍访问已删除会话、路由参数或陈旧状态的问题；
- 401 被前端一律解释为登录失效、刷新令牌失败或并发刷新竞争；
- grounded_chat 缺少 knowledge_base_id 时直接抛出未处理 ValueError；
- 模型列表刷新成功但为空、错误吞噬、格式解析错误和 Provider 差异；
- 空值、边界值、重复提交、并发操作、取消请求和网络中断；
- 数据删除是否完整，是否留下孤儿记录、文件或向量；
- 数据库约束、唯一性、级联、分页、排序、时间与时区问题；
- React stale closure、错误依赖、未清理副作用、状态竞争和 key 使用错误；
- 异常被过度捕获、日志缺少上下文、敏感信息进入日志等问题。

对每个 Bug 给出最短复现路径、预期结果、实际结果、根因证据、修复方向和回归测试建议。

D. 可维护性

- 命名、类型注解、模块职责和代码可读性；
- 重复逻辑、魔法值、过长函数、过度嵌套和隐式副作用；
- Pydantic Schema、ORM Model、领域模型是否混用；
- API 错误响应是否统一、可定位且适合前端展示；
- 前端请求、鉴权、错误处理、Toast 和表单逻辑是否重复；
- 注释是否准确，是否存在过时代码、死代码、临时补丁和 TODO；
- 依赖版本、锁文件、迁移脚本、示例配置和本地开发流程是否可靠；
- 是否容易为关键逻辑编写单元测试。

E. 可扩展性

- 新增 AI Provider 是否需要修改大量条件分支；
- Provider 能力是否通过统一接口和 capability metadata 表达；
- 模型是否能携带真实能力、输入/输出模态、上下文长度、地区和可用状态；
- 聊天模型、嵌入模型、图片和语音模型能否被正确分流；
- 是否支持“未指定模型时获取可用目录，指定模型时只暴露指定模型”的连接逻辑；
- 嵌入模型是否作为知识库级配置持久化；
- 是否保存 embedding provider、model、dimension、distance metric 和版本；
- 是否阻止同一向量空间混用不兼容嵌入；
- 更换嵌入模型时是否有重建索引、迁移和状态管理机制；
- 是否容易替换向量数据库、文档解析器、Chunker、Retriever、Reranker；
- 数据量、并发用户和模型连接增大后可能出现的瓶颈。

F. 可用性与产品体验

- 用户是否知道下一步该做什么；
- 表单标签是否明确指出 API Key、Base URL、地区、模型等字段；
- 必填项、格式、风险和示例是否清晰；
- 测试连接、保存连接和刷新模型的含义是否容易混淆；
- 成功、失败、加载、空数据、部分成功和重试反馈是否准确；
- 错误信息是否可操作，是否保留用户表单内容；
- 危险操作是否有确认、撤销或恢复方案；

G. 前端视觉与设计系统

- 页面布局、视觉层级、间距、对齐、字号、色彩和信息密度；
- 表单、按钮、弹窗、卡片、列表、导航和空状态是否一致；
- hover、focus、disabled、loading、error、success 状态是否完整；
- 是否存在文字截断、溢出、布局跳动、遮挡或响应式问题；
- 深浅色、对比度和可读性；
- 图标语义、按钮层级和危险操作表现；

- 视觉风格是否符合 AI 知识平台的可信、专业和高效定位。

若环境可安全启动，应检查核心页面实际渲染效果；如果不能启动，请基于组件与样式代码审查，并明确说明视觉结论的验证限制。

H. AI Provider 与模型目录

- Provider 抽象、连接配置和能力声明是否合理；
- DeepSeek、阿里云百炼、OpenAI 兼容接口等差异是否被正确处理；
- Base URL、地区、鉴权头、超时、重试和错误映射是否正确；
- 模型目录能否从官方 API 获取；若官方不提供完整目录，是否有可靠的静态目录或受控回退；
- 模型元数据来源、刷新策略、缓存时间、失效机制和人工覆盖；
- 不要仅根据模型名称猜测类型；若只能启发式推断，必须标注置信度和未知类型；
- 用户指定模型时是否尊重白名单，未指定时是否返回连接可用的模型；
- 测试连接是否测试了真正的凭据/区域/端点组合，而不只是网络可达；
- 错误是否正确区分鉴权失败、地区错误、模型无权限、限流和服务不可用。

I. RAG 与向量嵌入

- 文档解析、清洗、切分、元数据、批处理和失败恢复；
- Chunk 大小、重叠、语言和文档类型策略是否合理；
- 本地与在线嵌入模型的统一抽象和配置方式；
- 在线嵌入的成本、延迟、限流、隐私、批大小、重试和可观测性；
- 向量维度与索引 schema 是否匹配；
- 查询与入库必须使用兼容的相同嵌入空间；
- 同一知识库是否禁止任意混用不同嵌入模型；如果允许多个索引，是否明确隔离；
- 更换嵌入模型是否触发全量重嵌入；
- 检索 top-k、阈值、混合检索、重排序、引用和防幻觉机制；
- 是否有离线评测集和 Recall@K、MRR、nDCG、答案正确性/忠实度等评估方法；
- 重点评估使用阿里云百炼在线向量模型替换或补充本地 nomic-embed-text 的可行性，并给出推荐架构，而非只给一句“可行/不可行”。

J. 数据库与数据一致性

- ORM 实体关系、索引、外键、唯一约束、级联行为和迁移；
- 用户数据隔离和越权访问风险；
- 会话、消息、连接、模型、知识库、文档、Chunk 与向量记录的生命周期；
- 删除、重试、失败任务和并发更新下的一致性；
- 是否存在 N+1 查询、无界查询、低效分页或重复提交；
- SQLite 与生产数据库之间的兼容性风险；
- 敏感字段是否加密，密钥轮换和历史密文如何处理；
- 备份、恢复、清理和数据迁移能力。

K. 安全与隐私

- 密码、JWT、Cookie、CORS、CSRF、刷新令牌和会话策略；
- API Key 的输入、传输、加密、脱敏、日志和返回值；
- IDOR、越权、注入、SSRF、任意文件访问和路径穿越；
- 上传文件的扩展名、MIME、大小、解析器安全和恶意内容；
- Prompt injection、知识库数据泄漏、跨用户检索和工具调用风险；
- 错误堆栈是否暴露内部路径或敏感配置；
- 依赖与容器配置中的明显风险；
- `.env`、数据库、上传文件和运行日志是否可能被错误提交。

L. 性能与稳定性

- 阻塞 I/O 是否运行在异步事件循环中；
- HTTP 客户端、数据库连接和模型客户端是否合理复用；
- 超时、重试、指数退避、熔断、取消和限流；
- SSE/流式请求断开后的资源回收；
- 大文件、批量嵌入和并发索引的内存/CPU 风险；
- 缓存是否正确，是否可能返回过期或跨用户数据；
- 前端首屏、Bundle、重复请求、重渲染、长列表和资源加载；
- 健康检查、结构化日志、request ID、指标、追踪和告警；

M. 测试与质量保障

- 单元测试、集成测试、API 测试、前端组件测试和端到端测试覆盖；
- 核心路径、失败路径和历史 Bug 是否有回归测试；

N. 文档、实现与未完成功能

全面搜索以下线索：

- TODO、FIXME、HACK、XXX、NotImplementedError、pass；

五、优化方向

除缺陷外，请主动识别可以提升项目价值的优化机会，但必须与当前项目实际情况相关。至少从以下层面提出建议：

1. 快速收益：低风险、低成本、能明显改善稳定性或体验的改动。
2. 架构治理：减少耦合、建立统一 Provider/模型能力层、清晰事务和领域边界。
3. 产品体验：减少配置步骤、改善首次使用路径、错误自助排查和操作反馈。
4. AI/RAG 质量：嵌入策略、混合检索、重排、引用、评测体系和模型路由。
5. 性能成本：模型调用成本、缓存、批处理、并发控制、前后端性能。
6. 工程效率：代码生成、契约同步、测试夹具、CI、开发脚本和文档。
7. 安全合规：凭据保护、权限、审计、数据生命周期和隐私策略。
8. 可观测性：日志、指标、追踪、错误聚合、使用量和成本监控。

每个优化项都要给出：现状、目标、收益、代价、风险、依赖、实施步骤、验收指标。避免“优化代码结构”“提升性能”等空泛表述。

六、验证方式

在不修改项目的前提下，尽可能执行现有检查：

- 后端测试、lint、格式检查和类型检查；
- 前端 lint、类型检查、测试和生产构建；
- OpenAPI、路由和前端请求契约对照；
- 搜索未实现标记和可疑异常处理；
- 检查数据库迁移与 ORM 的一致性；
- 若可安全启动，验证核心页面和关键 API；
- 对关键 Bug 给出可自动化的回归测试方案。

记录每条命令、结果、失败原因和验证限制。不要将“命令无法运行”误写成“功能有 Bug”，但要说明为什么无法完成验证。

七、评级标准

严重程度：

- P0 / Critical：数据泄漏、凭据泄露、严重越权、数据破坏、系统不可用。
- P1 / High：核心功能失败、常见路径出现 500、数据不一致、重大安全风险。
- P2 / Medium：部分功能异常、边界条件 Bug、明显可维护性或体验问题。
- P3 / Low：低影响缺陷、代码气味、轻微视觉或文档问题。

证据置信度：

- Confirmed：已从代码或可复现结果确认。
- Highly likely：调用链证据充分，但受环境限制未实际复现。
- Risk：当前尚未触发，但设计上存在明确风险。
- Suggestion：非缺陷性质的优化建议。

工作量：

- XS：少于半天；
- S：约半天至一天；
- M：约 2—5 天；
- L：约 1—2 周；
- XL：需要跨模块或分阶段实施。

八、输出文件

将最终报告写入项目根目录：PROJECT_AUDIT_REPORT.md

报告至少包含以下章节：

1. 执行摘要
2. 项目现状与总体评分
3. 系统架构与核心数据流
4. 审查范围、方法和验证限制
5. 关键发现总表
6. P0/P1 高优先级问题
7. Bug 与正确性问题
8. 功能完整性矩阵
9. 已提及但未实现/未闭环功能
10. 项目结构与架构评估
11. 可维护性评估
12. 可扩展性评估
13. AI Provider 与模型目录评估
14. RAG 与嵌入模型评估
15. 数据库与数据一致性评估
16. 安全与隐私评估
17. 性能、稳定性与可观测性评估
18. 测试与质量保障评估
19. 可用性与用户流程评估
20. 前端视觉与设计系统评估
21. 开发体验、部署与文档评估
22. 优化机会清单
23. 分阶段改进路线图
24. 建议新增的测试清单
25. 已执行命令及结果
26. 待人工确认事项

总体评分使用 0—10 分，并分别评价：架构、功能完整性、正确性、可维护性、可扩展性、安全性、性能稳定性、测试、可用性、前端视觉、文档与运维。每项必须说明评分依据，不能只给数字。

九、发现项格式

每个问题使用统一格式：

- ID：例如 BUG-001、SEC-001、ARCH-001、UX-001。
- 标题：一句话准确概括。
- 严重程度：P0/P1/P2/P3。
- 置信度：Confirmed/Highly likely/Risk/Suggestion。
- 影响范围：用户、模块、数据或运维影响。
- 证据：文件路径、行号、函数/组件/API、测试或日志结果。
- 触发/复现方式：尽可能给出最短步骤。
- 根因：说明为什么发生，而不是复述现象。
- 修复建议：给出具体技术方案；必要时提供方案 A/B 及取舍。
- 验证方式：如何确认修复成功且没有回归。
- 工作量：XS/S/M/L/XL。
- 依赖与风险：实施前置条件和可能副作用。

十、路线图

根据依赖关系和收益，将建议分为五个阶段：

- 阶段 0：立即止血——P0/P1、安全、数据损坏和核心路径 500。
- 阶段 1：稳定核心流程——鉴权、连接、模型目录、聊天、知识库、删除和错误处理。
- 阶段 2：工程治理——架构边界、统一错误、类型契约、测试和 CI。
- 阶段 3：体验与性能——首次使用、视觉系统、性能、缓存和可观测性。
- 阶段 4：能力扩展——多模态、在线嵌入、混合检索、重排、评测和更多 Provider。

每个阶段说明目标、任务、依赖、预估工作量、风险和可量化验收标准。

十一、质量要求

- 结论必须具体、可验证、可执行。
- 不得制造不存在的功能或 Bug。
- 不要把代码风格偏好当成严重缺陷。
- 不要只给通用最佳实践，要结合当前代码证据。
- 不要重复同一个根因形成大量问题；可以合并并列出多个影响点。
- 优先关注用户真实路径和系统性根因，而不是机械罗列小问题。
- 报告既要覆盖全面，也要突出最值得先做的 5—10 项工作。
- 对无法确认的内容明确标注“待验证”以及需要的环境或信息。

十二、完成条件

只有在完成项目地图、核心调用链、关键功能追踪、Bug/风险审查、未实现功能核对、优化分析、验证记录和路线图之后，才算完成。

完成后：

1. 写入 PROJECT_AUDIT_REPORT.md。
2. 在最终回复中简要给出总体结论、最高优先级问题、报告文件路径和未能验证的内容。
3. 不要自动进入大规模修复阶段。
4. 等待用户选择要实施的修复或优化项，再制定实施计划。
